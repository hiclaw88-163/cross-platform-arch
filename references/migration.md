# 存量项目移植规范（Migration）

> 适用场景：把一个**已有项目**的功能迁入「一核多端」架构（重构/重写/换壳）。
> 本规范来自真实事故：某移植项目把旧引擎 8k 行整体搬进适配器层、core 只剩
> 195 行薄壳——架构分层"形似神不似"，业务规则散落外圈，最终产生了
> "dry_run 试运行静默降级成真实执行"的严重缺陷。

## 核心裁定：搬运 ≠ 移植

| | ❌ 照搬（搬运） | ✅ 移植 |
|---|---|---|
| core | 只有循环 + 汇总的薄壳 | 领域词汇 + 业务规则的**唯一出处** |
| 编排语义 | 散在 bridge/路由/端里 | 集中在 core 用例层 |
| 结果词汇 | 端上各自维护映射表 | core 枚举单源,端零映射 |
| 适配器 | 原样转发旧入口 | 只做形状转换,不做语义决策 |

判断口诀：**"这个业务规则改一下,要改几个文件?"** 超过 1 个（core 之外）,
就是没有归位。

## 五步流程（每步有可验证产物）

### 第 1 步：功能清单分析（不许跳过）

通读旧项目,产出**功能 → 技术能力映射表**（写入 `docs/migration-notes.md`）:

```
旧功能             | 本质           | 归属
-------------------+----------------+--------
每日签到领积分      | 业务编排        | core 用例
"已签过就不再领"    | 幂等规则(业务)  | core 用例/领域
结果 OK/ALREADY/…  | 领域词汇        | core domain
HTTP 调用/重试      | 技术能力        | engine 适配器
凭据解密            | 技术能力        | engine 适配器
SQLite 台账         | 技术能力        | engine 适配器
系统定时任务注册     | 技术能力        | engine 适配器
```

红线：凡是"如果换一种业务它还成立"的（幂等、试运行语义、空集解释、
状态分类），都必须进 core；只有"换了业务就不成立"的（HTTP/CDP/解密）才留适配器。

### 第 2 步：领域词汇提取（先写 core 再碰 engine）

- 结果全集收进 `domain/results.py` 枚举，**字面量与旧系统方言对齐**
  （翻译零损耗），并提供 `from_engine(text)` 作为唯一翻译入口；
- 每个枚举值配**语义分类谓词**（`is_pass / is_fail / kind`）——端上渲染
  和汇总只准消费分类谓词，禁止自己再写 `if status in [... 表]`；
- 别名表（旧系统长尾叫法 → 领域词汇）也放 core，适配器不放。

### 第 3 步：编排语义上移用例层

以下规则**只写在 core 用例里**，适配器无权执行或放宽：

- **硬承诺**：如 `dry_run=True` 只报告不领取。适配器不支持时用例层直接
  拒绝执行（返回失败结果），**绝不静默降级**——真实事故就出在这里；
- **能力声明**：端口加 `capabilities()`，适配器从自己的实现签名如实申报
  （如函数签名里没有 `dry_run` 形参 → 申报不支持），用例据此执法；
- **空集语义**："不指定目标 = 全部启用目标"是业务规则，进用例层；
- **校验**：未知编码立即失败，不许"打错名字静默成功"。

### 第 4 步：技术能力留适配器

旧代码中 HTTP 客户端/CDP 编排/凭据解密/SQLite/调度器等**保持原样搬入
适配器包**（它们是被验证过的，不重写）。但适配器对 core 只做三件事：

1. 实现端口方法（形状转换）；
2. 如实申报 capabilities；
3. 从事实来源（台账/落库）回填**结构化**结果——不要只返回退出码二值,
   更不要让端去解析日志文本。

### 第 5 步：端零映射验收

- `grep` 各端源码，不得出现结果语义映射表（如 `PASS_RESULTS = [...]`）；
- 端消费的都是 core 出产的词汇（API 返回归一化 status + kind 分类）；
- 跑 `verify_project.py --test` 全绿。

## 机器可查红线（verify_project.py 已覆盖/计划）

| 红线 | 检查方式 |
|---|---|
| core 零框架依赖 | verify 检查项 2（AST 级） |
| token 引用闭合 | verify 检查项 4 |
| core 不被端绕过 | verify 检查项 3 + grep 端源码不得 import 引擎内部模块 |
| 无空包残留（改名后死目录） | verify 检查项 7（`check_empty_packages`） |
| 端零结果映射 | 人工 grep（暂无自动检查,评审时必查） |
| core 不是薄壳 | 人工评审：用例层必须有≥1 条"没有它端就会做错"的规则 |

## 改名/重构后的清场规程（2026-11-07 事故）

**事故**：把 `owk_engine/store` 改名 `ledger`、`apps/` 改名 `extensions/`、
`kit/`→`signin/`、`scheduledomain/`→`scheduling/` 时，只搬了文件没删旧目录。
Python 3 把**没有 `__init__.py` 的空目录**当成命名空间包，于是：

```python
from owk_engine import store   # 不报错！
store.record_payload(...)      # AttributeError —— 被 best-effort 的 except 吞掉
```

结果：CLI 输出一切正常，**台账静默丢失一整天**，dashboard 一片空白，
排查时还以为是"没跑过"。这比直接 ImportError 危险得多——它伪装成健康。

**规程（改名后必须逐条做）**：

1. 全量搜索旧名残留：`grep -rn "旧模块名" --include="*.py"`，包括
   import、字符串形式的模块路径（entry-points、`importlib` 表）、docstring；
2. **删掉旧目录本身**，不要只清空内容——空目录会变成"假成功的导入"；
3. 跑 `verify_project.py`，检查项「无空包残留」必须 PASS；
4. 对 best-effort 路径（`except Exception: pass`）逐个确认：**失败必须留痕**
   （stderr 告警一次 / 计数器），静默吞异常只能用于真正的可选项；
5. 回归用例钉住副作用：落库、写文件、发通知这类"看不到但很重要"的动作，
   要有一条"真的写进去了"的测试，而不是只测返回码。
